§1 — Invariants

Rules the database enforces

These are not application conventions. Each one is a constraint, enum or foreign key in the schema itself, so a bad write fails at the database rather than slipping through a missed validation in the API.

requested_quantity > 0

A line item cannot be raised for zero or negative quantity. Enforced by a CHECK constraint on request_items, alongside bounds keeping approved quantity within the requested amount.

budget_heads.head_type

Every budget head carries a financial classification — Revenue or Capital — as a Postgres enum, separate from the finer per-item type.

Originals are never overwritten

Partial approval writes approved_quantity and approved_amount alongside the requested values. The request as raised stays intact and auditable forever.

Financial year only

Requests are scoped to a financial year. Academic year is deliberately absent from the model; carry-forward moves a request between financial years while linking back to the original.

Roles are data, not code

Adding a CDC member is an INSERT into stage_approvers, not a deployment. Any stage supports any number of approvers.

Routing is configurable

Amount thresholds live in stage_routing_rules. The ₹50,000 and ₹5,00,000 boundaries are rows that can be edited, not constants compiled into the application.

Comments carry visibility

A CDC remark scoped UP_CHAIN reaches the Principal and above, but never leaks down to the Purchase Committee or the original requester.

Files live outside the database

Quotations, bills and scanned approvals go to object storage. attachments holds only the pointer, type, size and uploader.

Figure 1 — Actors

Use case diagram

Who can do what. Six actor types map onto twenty use cases; the approval verbs (approve, partially approve, reject, escalate) repeat across four authority levels, which is exactly why they are driven by one shared workflow engine.

Figure 2 — Routing

Approval workflow

A request enters at the stage whose amount window contains its total, then escalates upward. Each authority holds the same four verbs; only Chairman + Vice Chairman cannot escalate further.

Figure 3 — Data model

Entity relationship diagram

The full relational model, matching db/schema/*.sql exactly. The centre of gravity is requests → request_items → approval_action_items, which is what makes item-level partial approval possible.

Figure 4 — Domain model

Class diagram

The application-layer view. Beyond the persisted entities it names two services — WorkflowEngine and NotificationService — which hold the behaviour that would otherwise be duplicated across four approval stages.

Figure 5 — Lifecycle

Request state diagram

Fourteen states, not two. The current status answers where is this request now; the audit trail answers everything that happened before it got there.

Figure 6 — Interaction

Escalation sequence

One ₹6,00,000 request travelling from a department head to Chairman + Vice Chairman, ending in a partial approval of ₹2,50,000 — and every row the database writes along the way.

§3 — Setup

Running it

Two interchangeable paths. The local install listens on 5432, the Docker stack on 5433, so both can run side by side without colliding.

Local PostgreSQL

psql -U postgres -c "CREATE DATABASE spc_approval;"
psql -U postgres -d spc_approval -f db/run_all.sql

Docker

cd db
docker compose up -d
# Postgres on localhost:5433 · pgAdmin on localhost:5050

The container auto-loads every schema and seed file on first start. To rebuild from scratch, docker compose down -v drops the volume so the init script reruns.
